# Redmine Feature 需求互動建立 (`/redmine-feature-create`)

這是一個**主動式**的 skill：不是單純講規範，而是實際陪使用者把一張 Feature 需求單問到夠
具體、組好格式、使用者點頭之後才真的建立到 Redmine。判斷「夠不夠具體」的標準來自
`redmine-feature` skill 歸納的真實案例對照（籠統 vs 具體的寫法），這裡不重複列一
次對照表——**前置 2 會明確要求先把那份 skill 實際載入**，不要只憑名稱印象憑空判斷，只講
**互動流程本身**要怎麼跑。

本 skill 隨組織 Claude Plugin（plugin 名稱 `redmine`）發佈。規格單一事實來源是 Redmine
議題 "#26313":https://redmine.nineder.com/issues/26313 （並繼承
"#26311":https://redmine.nineder.com/issues/26311 基本寫入準則的全部條款）——之後要修改本
skill 的內容，先修訂 #26313 再同步這份檔案。

**回覆時的輸出格式（承 #26311 第 16 條）**：對使用者說話時，提到任何 Redmine 議題編號都要
輸出成指向 `https://redmine.nineder.com/issues/編號` 的超連結，不要只留純文字編號；使用者
訊息裡出現的編號同樣適用。Claude Code 桌面版**一般點擊**會落在內建的 Claude Browser（該處
沒有 Redmine 登入 session、顯示的是登入頁），**Cmd+click** 才會外開到系統預設瀏覽器——使用
者回報開在登入頁時，提示他改用 Cmd 加點擊。

## 前置 1 — 確認 Redmine MCP 連線

跟 `redmine` skill 的步驟 1-2 一樣的檢查方式——呼叫 `get_current_user`，沒有這個工具或
呼叫出錯，就照 `redmine` skill 的步驟 2 引導使用者完成 `claude mcp add`/`claude mcp login`
（含 `--scope user`），設定好之後才繼續下面的訪談流程。不要在連線都還沒確認的情況下，花
使用者時間問完一整輪問題卻建立不了議題。

## 前置 2 — 實際載入 `redmine-feature` 的判斷標準

**用 Skill tool 明確呼叫一次 `redmine-feature`**（在 plugin 環境下，技能清單裡的名稱可能
顯示為 `redmine:redmine-feature`，用清單裡實際出現的那個名稱呼叫），把它的好壞對照表、判
斷方法真的載入這次對話的 context 裡，不要只因為看到這個名字、憑印象或憑猜測就自己判斷
「夠不夠具體」——單純提到一個 skill 的名字不會讓它的內容自動出現，必須真的呼叫才會載入。
這一步只需要做一次，之後步驟 2 逐格訪談時才有真正的判斷依據可以用。

## 步驟 1 — 先問要開在哪個專案

問使用者這張需求要開在哪個專案（可以是 Redmine 專案名稱、identifier，或直接給
`redmine.nineder.com/projects/xxx` 的網址）。如果使用者不確定，呼叫 `list_projects` 列出來
讓他選。拿到 `project_id` 之後才進下一步——不同專案的必填欄位可能不同（`create_issue` 呼叫
失敗時錯誤訊息會指出缺哪個欄位，之後可以照著補，不要因此卡住整個流程）。

## 步驟 2 — 逐格訪談，籠統就追問

依序問以下六格，**每答一格就立刻用前置 2 載入的 `redmine-feature` 判斷方法檢查夠
不夠具體，不夠具體就當場追問一次，不要等到最後才回頭改**：

| 格 | 問法 | 太籠統時怎麼追問 |
| --- | --- | --- |
| 身為 (As a) | 「這個功能主要是哪一種身份/系統在用？」 | 如果答案是「使用者」「行銷人員」這種泛稱，追問：「具體一點——是哪個系統的使用者？有沒有綁定什麼身份（會員/團主/內部帳號）？」 |
| 我想要 (I want) | 「具體想要系統做什麼？」 | 如果答案只有方向沒有機制（如「加速流程」「簡化操作」），追問：「用什麼方式做到？例如新增一個按鈕/頁面/自動化規則，長什麼樣子？」 |
| 以至於 (so that) | 「達成之後，怎麼知道有達到？」 | 如果答案不可驗證（如「做更好的分析」「賺錢」），追問：「有沒有具體可以檢查的結果？例如某個數字變化、某個流程不用再手動做？」 |
| 假定 (Given) | 「這個情境開始之前，系統/使用者要處於什麼狀態？」 | 如果答案其實是「做完之後的結果」（例如「已模組化」），指出這其實是 Then 不是 Given，請使用者重新想「動作發生前」的狀態 |
| 當 (When) | 「使用者/系統做了什麼動作、或什麼時間點觸發？」 | 太籠統（如「進行操作」）就追問具體動作是什麼（點擊哪個按鈕、送出哪個表單、還是排程時間到） |
| 然後 (Then) | 「結果應該長怎樣？怎麼驗收？」 | 太籠統（如「可以記錄下來」）就追問：記到哪裡、格式是什麼、之後誰會用、用在哪 |

**多步驟流程判斷**：如果在訪談中發現這個需求本質上是多階段流程或狀態機（例如審核流程、
分潤流程、跨角色交接），主動跟使用者說「這個聽起來有好幾個階段，我們一段一段拆成多組
當/然後，一步一狀態」，重複問當/然後直到整條流程問完（參考真實案例 #23199 的八段式寫法）。

**允許留白的情況**：如果使用者能提供完整的畫面設計稿連結（Figma/Google Drive/截圖）且特性
描述已經講得很具體，可以問使用者「這個要不要用設計稿取代文字驗收標準？」——如果同意，
驗收標準留白但附加資訊一定要放上連結（參考 #25224 的模式），不能兩邊都空。

## 步驟 3 — 問附加資訊

主動問：「有沒有現成的畫面設計稿、API 文件、規格連結、或相關的其他 Redmine 議題編號可以
附上？」把工程師會需要的技術背景、已知限制、參考連結收進這一段，而不是留給後續 journal 慢
慢補。

## 步驟 4 — 組出完整格式，給使用者確認

**這一步組出來的內容要完整遵守 `redmine` skill「寫入 Redmine 的基本準則」（規格
"#26311":https://redmine.nineder.com/issues/26311 ）的全部條款**，其中跟組稿直接相關的
如下：

**重要：Redmine 的 Textile 表格儲存格裡，沒有任何跳脫符號能換行。** 打字面的 `\n`、`\r\n`
字串,或甚至打一個 `<br>` HTML 標籤,在表格儲存格裡全部都只會顯示成一串看得到的原始文
字,不會被解析成真正的換行(這是實際在 issue #26135 上試過三種寫法都失敗才確認的)。
`*` 條列符號在儲存格內同樣不會變成真正的清單,只會顯示成一個字面的星號。

所以,只要「我想要 (I want)」「以至於 (so that)」「當 (when)」「然後 (then)」裡任何一格的
內容累積到兩項以上(訪談過程中使用者一直追加需求、或本質是多步驟流程),組格式時**改用數
字編號(`1.` `2.` `3.`)配合真正的換行字元分隔每一項**——也就是在準備要送給 `create_issue`
的 description 文字裡,直接放進真正的斷行(換行符本身),而不是任何一種跳脫符號組成的字
串。子項目(例如某一大項底下還要再拆細項)可以用 `2-1.` `2-2.` 這種編號延伸,一樣用真正換
行分隔,不需要靠 Textile 的巢狀清單語法(那個在儲存格內同樣不會被解析)。

**超連結前後要留空白，長內容要用 Collapse 收合**：整份 description（不只是表格儲存格
內，附加資訊段落一樣要遵守）裡任何超連結（`"文字":https://...`）前後都要留一個半形空白，
不能直接緊貼中文字或其他文字——緊貼的話 Redmine 介面轉譯時容易把連結範圍跟旁邊的字混在
一起，變成介面錯亂。例如附加資訊裡提到參考議題，要寫成「參考 "#26135":https://... 這張」
（前後各一個半形空白），不要寫成「參考"#26135":https://...這張」。如果附加資訊裡要貼程式
碼，**不分行數**一律用 `<pre>` 包起來（語言在 Redmine 內建清單內時裡層加
`<code class="lang">`），再用 Redmine 內建的 `{{collapse(標題文字)...}}` macro 包起來預設收
合，並在收合外面補一句結論——不要用三個反引號的 code fence，舊的「10 行以內免收合」門檻已
廢除。之後如果要在議題上追加 journal Note，超過 4 行的過程描述也一樣：重點摘要放 Note 開
頭，細節用 collapse 收合。

**送出前一定要驗排版**：這個模板整份都是 Textile 表格，最容易被下面這個坑一次炸掉——寫進
Redmine 的內容裡，行內的 `@...@` **絕對不能包角括號形式的標籤**（`<pre>`、`<code>` 等）。
`@` 本身就會產生 `<code>`，內容再帶一個同名標籤會變成沒有收尾的巢狀標籤，**從那一行起所有
表格都不會被解析**，畫面上只剩字面的 `|={background-color: ...}.`，而且 Redmine 完全不報
錯（事故實例 #26537）。組稿完成後、呼叫 `create_issue` 之前，逐行確認每行的 `@` 數量成對、
成對區間內不含 `<`；要說明標籤就寫成「pre 標籤」這類文字敘述。

用公司固定格式組出完整 textile 內容：

```
*[特性描述(Feature Description)]*

|={background-color: #cfcfcf;}. 身為一位 (As a) | ... |
|={background-color: #cfcfcf;}. 我想要 (I want) | ... |
|={background-color: #cfcfcf;}. 以至於 (so that) | ... |

*[驗收標準(Acceptance Criteria)]*

|={background-color: #cfcfcf;}. 假定 (Given) | ... |
|={background-color: #cfcfcf;}. 當 (when) | ... |
|={background-color: #cfcfcf;}. 然後 (then) | ... |

*[附加資訊(Additional Information)]*

...
```

完整貼給使用者看過一遍，明確問「這樣可以建立了嗎？」——**在使用者明確同意之前，不要呼叫
`create_issue`**。這是會在 Redmine 留下真實紀錄的寫入動作，跟單純聊天草稿不一樣。

## 步驟 5 — 建立議題

使用者確認後才呼叫 `create_issue`（`project_id`、`subject`、上面組好的 `description`，以及
使用者有提到的 `assigned_to_id`/`due_date`/`tracker_id` 等）。如果因為缺必填欄位失敗，錯誤
訊息會指出缺什麼，跟使用者確認後補上重試。建立成功後回報議題連結。

### 步驟 5.5 — 如果一開始有參考議題，自動建立正式 Related issues 關聯

如果使用者在對話一開始或訪談過程中提供了其他 Redmine 議題（例如貼了
`redmine.nineder.com/issues/XXXXX` 的網址，或說「這張是延伸自 #XXXXX」「參考 #XXXXX」），
不要只把它寫進附加資訊的文字連結就結束——建立議題成功、拿到新議題 id 之後，緊接著針對每一
個被提到的參考議題呼叫 `create_issue_relation`（`issue_id` 用剛建立的新議題、`issue_to_id`
用參考議題、`relation_type` 預設用 `relates`，除非使用者的說法明確指向其他類型，例如「這張
被那張擋住」→ `blocked`/`blocks`，「這張跟那張重複」→ `duplicates`），讓 Redmine 議題頁面的
「Related issues」區塊出現正式的雙向關聯，不是只有文字提及。

**`precedes`/`follows` 要特別小心，不要拿來表示「相關」或「這是後續工作」**：建立這兩種關
聯時，Redmine 會**自動重排後續議題的 start_date/due_date**——開始日被推到前置議題到期日的
隔天，到期日再依原本工期往後平移，過程沒有任何提示（實例：#26537 原本填
2026-08-15/2026-10-31，設了 `follows #26534` 之後立刻被改成 2026-10-01/2026-12-17）。只有
使用者真的在講排程上的先後順序、而且接受日期被自動計算，才用 `precedes`/`follows`；其餘一
律 `relates`。已經誤設的話，刪掉關聯**不會**把日期還原，要另外用 `update_issue` 改回原值。

## Status 分工規劃

角色定義（依公司規則，不是猜測）：**開發人員** = 耐德科技-資訊部-程式組、耐德科技-資訊部
-系統組。目前實際觀察到、持續在做開發/上線/commit 這類事的成員：林茂昇 watsonlin、
蘇上凱 hogansu、呂柏諺 charleslu、王特成 techengwang、張穎秦 jacob.chang、陳昶任 delight。
**除此之外的所有人**（業務、行銷、各專案窗口、PM 等）一律視為**需求者**。

這張表是依過去約 100 筆 Feature 議題的實際 journal 紀錄歸納出來的，不是憑空定義：

| Status | 意義 | 誰負責設定 |
| --- | --- | --- |
| New | 議題剛建立，還沒人動工 | 建立議題的人（通常是需求者），`create_issue` 預設值，不用手動選 |
| In Progress | 開發人員已經開始處理 | 開發人員 |
| Feedback | 卡住、等對方回應才能繼續 | 雙方都可能設定——由「正在等對方回覆的那一方」設，不限定是哪一邊 |
| Resolved | 開發人員認為功能已完成，交付需求者驗收 | 開發人員 |
| Closed | 真正結案 | 實務上多由開發人員直接關閉；理想情況應該是需求者驗收確認後才關，訪談時可以提醒使用者這件事 |
| Limitation | 不開發／暫緩 | **需求者或更高層的商業判斷**，不是開發人員能片面決定的技術判斷——即使是開發人員在 Redmine 上點下去，也應該是代為記錄別人的決定，不是自己判斷 |
| Reopened | Closed 之後又要重新處理 | 需要繼續處理的一方主動 Reopen，不要在 Closed 議題上默默繼續加東西 |

### 建立議題時預設 New，不用特別問

`create_issue` 不用手動指定 status，預設 New 就是需求者建立議題的起點。只有使用者本身就是
開發人員、且明確表示要立刻動工時，才問「要不要直接設成 In Progress？」。

### Closed 議題不能默默塞新需求——要 Reopen 或開新單

過去樣本裡多次出現「議題已經 Closed，需求者又在同一張追加新範圍，開發人員做完後只是再貼一
次『已完成』，但 Status 欄位從頭到尾沒反映這個往返」的情況（例如 #22846、#24768、#23110）。
在 `/redmine-feature-create` 的互動過程中，如果發現使用者描述的其實是**某張已 Closed 議題的延伸**，
要主動提醒、並在兩個做法中選一個，**不要讓對話默默把新需求塞進舊的已結案議題**：

1. 本質是同一件事的延續 → 建議把舊議題 Reopen
2. 本質是新範圍 → 開一張新議題，附加資訊裡連結回舊議題編號（例如 `related to #12345`）

## 這個 skill 存在的目的

跟 `redmine-feature`（被動的撰寫規範、給 review 別人需求單用）不同，這個 skill
是主動幫忙「現在就把一張需求問清楚並建出來」。最終檢驗標準：**這張議題如果現在指派給一個
完全沒參與過討論的工程師，或是丟給另一個沒有任何上下文的 Claude 對話，能不能單看這張 issue
的內容就懂該做什麼、怎麼驗收**——如果不確定，代表訪談還沒問到位，回到步驟 2 繼續追問。
