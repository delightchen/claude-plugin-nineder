# Redmine Bug 撰寫規範（現象 → 根因 → 影響 → 修法 → 驗證）

這份 skill 不是發明新格式——判斷依據來自 2026-08-08 對 Bug tracker **全量 453 條議題
（2020-06 ~ 2026-08）**的分析：2020-2021 年有 304 條套用公司舊的 9 段 QA 模板，但其中
**只有 6 條**真正把重現步驟＋預期結果填滿，其餘全是空模板骨架；而 2026 年寫得好的工程型
Bug（#26272、#26147、#25846、#25514、#25553、#26301）收斂出一套一致的結構。這份 skill
把那套結構歸納成規範。

**定位**：這是**被動**的撰寫規範／review 用 skill，**絕不執行任何 Redmine 寫入動作**——
需要「實際建立議題」時是另一個 skill `redmine-bug-create` 的事。本 skill 的規格單一事實
來源是 Redmine 議題 "#26314":https://redmine.nineder.com/issues/26314 （並繼承
"#26311":https://redmine.nineder.com/issues/26311 基本寫入準則的全部條款）——之後要修改本
skill 的內容，先修訂 #26314 再同步這份檔案。

## 標題公式

```
[系統/模組] 一句話現象 — 根因或量化影響
```

- 現象講「使用者／系統看到什麼」，破折號後放已知根因或量化衝擊。
- 正例：`[急][票券] 藍新信託授權餘額不足，電子票取號排程停擺 — 762 張票卡住、客人付款拿不到票`（#26301）、
  `[ ASO ] NAS pickup_module watermark 精度 bug 造成簡訊轟炸：repoint 到 PG 後同筆每 10 分鐘重發一次飛信`（#25514）
- 反例：`訂單狀態異常`、`XX功能有問題`——只有模組沒有現象，列表頁掃過去不知道嚴不嚴重。

## 先分流：你是「回報者」還是「已完成調查」？

寫之前先判斷這張單處在哪個階段，兩種結構不要混用：

### A. 回報型（只看到現象、根因未知）— 五段精簡結構

| 段落 | 要填什麼 | 太弱的寫法 | 具體的寫法 |
| --- | --- | --- | --- |
| 現象 | 一句話講清楚「誰、在哪、看到什麼」 | 「訂單狀態異常」 | 「TAP-CVS 及 711 訂單已回覆成交檔，但訂單狀態未更新」 |
| 發生位置／環境 | 哪個系統、頁面、單號——能讓工程師定位就好，不用硬套桌機 OS 硬體清單 | 整段留空的環境模板 | 「後台 admin.buty99.com/merchant_manage、供應商統編 12345678」 |
| 重現步驟 | 能重現才寫步驟；不能重現就記「發生時間＋當時做了什麼」 | 「1.（空）2.（空）」 | 「1. 測試匯入附件 SO 檔 2. 查看匯入的 SO 單 3. NI20201006000003 無帶入小盒子」（#1222） |
| 預期 vs 實際 | 兩者都要具體、可對照 | 「應該要正常」 | 「預期：SO 匯入自動帶入 Inventory Detail／實際：部分商品不會帶入」 |
| 證據 | 截圖、log 原文、錯誤訊息、實際單號——至少一樣 | 無 | 錯誤訊息原文、`SHL20260608174216514` 這種可以直接拿去查的單號 |

### B. 調查型（已查明或大致定位根因）— 五段調查結構

| 段落 | 要填什麼 | 好案例 |
| --- | --- | --- |
| 現象（含時間線） | 量化的症狀＋具體時間戳：幾筆、佔比、從何時開始、持續多久 | #26147「全 collection 最新 date_created 停在 2026-07-28T08:20:30Z，7/29-31 三天排程零產出」 |
| 根因（失敗鏈） | 從 code 一路推到現象：file:line、commit、設定值，逐步講「為什麼」 | #25553「ORDER BY X.account DESC 是字串字典序 → `-99` 永遠大於 `-100` → 第 101 家起永遠產生已存在帳號」 |
| 影響範圍 | 量化＋連鎖影響（會不會拖垮別的系統／議題） | #26147「所有 PowerBI visual 快照停更 → SyncVouchers 每天讀舊快照 → 23,918 筆 date_updated 全 null」 |
| 修法（分層） | 立即止血／根本修／可觀測性改善分開列，不混成一團 | #26147「①止血：補孤兒記錄外鍵 ②根本修：collate 加 null 防護 ③可觀測性：reject 分支補通知」 |
| 驗證方式 | 別人能照跑的查證指令＋能打勾的驗收條件 | #25514「黃金驗收：修完連跑兩次，第二次必須撈到 0 筆」；#26147 附三條可直接執行的 API query |

## 鐵則（兩種模式共用）

1. **空段落必刪**：填不出內容的段落整段刪掉，不留模板骨架。空模板不是「格式完整」，
   是雜訊（歷史反例 #326：9 段全空，只有第一段一句話）。
2. **量化鐵則**：「有時候會錯」不可驗收；「近 14 天 853 張票只有 68 張成功取號」才可以。
   影響一律帶數字：幾筆、佔比 %、持續多久、多少人。
3. **時間線用具體時間戳**：「16:27 權限異動 → 16:34 恢復 → 16:27~17:09 快取持續顯示全 0
   達 40 分鐘」（#26272），不要「一段時間之後」。
4. **根因不能只有結論**：「是快取問題」是結論不是根因；要寫出失敗鏈——哪一行 code、
   什麼輸入、如何一步步變成使用者看到的現象。
5. **關聯議題建正式 relation**：「根因來自 #25498」「連鎖影響見 #25936」除了行文提及，
   要在 Redmine 上建立 relates 關聯；行文引用寫 `{{issue(25498)}}` 或 `"#25498":URL`
   前後留半形空白。
6. **排版承 #26311**：數據對帳用 Textile 表格（`|_.` 表頭），code／log 用 `<pre>`，
   超過 10 行用 `{{collapse(標題)...}}` 收合。
7. **修正過程記錄用大綱＋collapse**：修 Bug 過程中在議題 journal 追加 Note 時，重要變動
   必須保留——改了哪些檔案／設定／資料、關鍵決策與轉折，用**大綱模式**記錄（數字或條列，
   一行一個重點）；大綱項底下若有細項（diff、指令輸出、逐步操作、長篇說明），用
   `{{collapse(標題)}}` 收合——讓 journal 讀起來先見大綱、展開才見細節，細節不淹沒重點。
8. **驗證要留畫面證據**：修復／調查完成後的驗證，只要結果能以畫面呈現（修好的頁面、跑通的
   流程、修正前後對比），就截圖或錄 GIF 留存為驗證證據放進收尾 Note，不能只寫「已驗證」一句
   帶過。這是**驗證方法論**（要不要留畫面、留什麼畫面），與 #26311 第 9 條「圖片的內嵌格式」
   不同；圖片呈現則沿用第 9 條——行內 `!檔名.png!` 內嵌、包進 `{{collapse(標題)}}`、標題寫清楚
   是什麼畫面（例「驗證：修復後首頁」）、預設收合（實作範例 #26316）。

## 撰寫前自我檢查清單

1. 標題單獨出現在列表頁，別人能不能判斷「是什麼壞了、多嚴重」？
2. 影響有沒有數字？（幾筆／幾 %／幾天）
3. 根因是「結論」還是「失敗鏈」？換一個工程師來讀，能不能沿著鏈自己驗證一遍？
4. 驗證段有沒有「照著跑就能複驗」的指令，和「打勾就能結案」的驗收條件？
5. 有沒有留著沒填的空模板段落？有就刪。
6. 提到的其他議題，relation 建了沒？
7. 修正過程的 journal Note 是不是大綱在外、細項收合？重要變動（改了什麼檔／設定／資料）
   有沒有留下來？
8. 驗證結果能不能截圖？能的話，收尾 Note 有沒有附上驗證畫面（行內內嵌＋`{{collapse}}` 收合＋
   標題）？

## 給 review 別人 Bug 單時使用

當使用者請你檢查/潤飾一份 Bug 描述時：先判斷它是回報型還是調查型，再逐段對照上表——
具體指出哪一段缺量化、哪裡根因只有結論沒有失敗鏈、哪裡驗證不可複驗，給出具體改法
（可引用上面好案例的寫法），而不是整份重寫——保留原本的業務語意與已有的事實。
