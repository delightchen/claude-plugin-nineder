# Redmine Bug 互動建立 (`/redmine-bug-create`)

這是一個**主動式**的 skill：實際陪使用者把一張 Bug 單問到夠具體、組好格式、使用者點頭
之後才真的建立到 Redmine。判斷「夠不夠具體」的標準來自 `redmine-bug` skill 歸納的真實
案例對照，這裡不重複列——**前置 2 會明確要求先把那份 skill 實際載入**。

本 skill 隨組織 Claude Plugin（plugin 名稱 `redmine`）發佈。規格單一事實來源是 Redmine
議題 "#26315":https://redmine.nineder.com/issues/26315 （並繼承
"#26311":https://redmine.nineder.com/issues/26311 基本寫入準則的全部條款）——之後要修改本
skill 的內容，先修訂 #26315 再同步這份檔案。

**回覆時的輸出格式（承 #26311 第 16 條）**：對使用者說話時，提到任何 Redmine 議題編號都要
輸出成指向 `https://redmine.nineder.com/issues/編號` 的超連結，不要只留純文字編號；使用者
訊息裡出現的編號同樣適用。Claude Code 桌面版**一般點擊**會落在內建的 Claude Browser（該處
沒有 Redmine 登入 session、顯示的是登入頁），**Cmd+click** 才會外開到系統預設瀏覽器——使用
者回報開在登入頁時，提示他改用 Cmd 加點擊。

## 前置 1 — 確認 Redmine MCP 連線

呼叫 `get_current_user`；沒有這個工具或呼叫出錯，就照 `redmine` skill 的步驟 2 引導使用者
完成 `claude mcp add`/`claude mcp login`（含 `--scope user`），設定好之後才繼續訪談。
不要在連線都還沒確認的情況下，花使用者時間問完一整輪卻建立不了議題。

## 前置 2 — 實際載入 `redmine-bug` 的判斷標準

**用 Skill tool 明確呼叫一次 `redmine-bug`**（在 plugin 環境下，技能清單裡的名稱可能顯示
為 `redmine:redmine-bug`，用清單裡實際出現的那個名稱呼叫），把它的兩種模式結構、好壞對照
與鐵則真的載入這次對話的 context——單純看到名字不會讓內容自動出現，必須真的呼叫才會載入。
這一步只需要做一次。

## 步驟 1 — 先問要開在哪個專案

問使用者這張 Bug 要開在哪個專案（Redmine 專案名稱、identifier，或
`redmine.nineder.com/projects/xxx` 網址皆可）。不確定就呼叫 `list_projects` 列出來讓他選。

## 步驟 2 — 分流：回報型還是調查型？

問一句：「**你已經查出根因了嗎？還是目前只看到現象？**」

- 只看到現象 → 走步驟 3（回報型訪談）
- 已完成調查（知道根因、或已定位到 code/資料層）→ 走步驟 4（調查型訪談）

## 步驟 3 — 回報型訪談（五段）

依序問，**每答一段就立刻用前置 2 載入的標準檢查，太籠統當場追問一次**：

| 段 | 問法 | 太籠統時怎麼追問 |
| --- | --- | --- |
| 現象 | 「一句話說：誰、在哪個系統、看到什麼不對？」 | 「有時候會錯」→「最近一次是什麼時候？哪一筆單／哪個帳號？」 |
| 發生位置／環境 | 「在哪個頁面／系統／單號上發生的？」 | 只要能讓工程師定位就好；不要硬套桌機 OS 硬體模板（歷史教訓：舊 9 段模板的環境段 98% 是空的） |
| 重現步驟 | 「照什麼步驟做會再看到一次？」 | 不能重現就改問「發生的時間點＋當時做了什麼」，照實記錄「無法穩定重現」 |
| 預期 vs 實際 | 「你預期看到什麼？實際看到什麼？」 | 「應該要正常」→「正常長什麼樣子？欄位值／畫面應該是什麼？」 |
| 證據 | 「有沒有截圖、錯誤訊息原文、log、實際單號？」 | 至少要一樣；都沒有就追問「當時畫面上看到什麼字？」錯誤訊息請使用者原文貼上，不要轉述 |

## 步驟 4 — 調查型訪談（五段）

依序確認，缺哪段追問哪段：

1. **現象＋時間線**：量化了嗎？（幾筆、佔比 %、從何時開始、持續多久）時間點有具體時間戳嗎？
2. **根因失敗鏈**：有 code 位置（file:line）、commit、設定值支撐嗎？能從輸入一步步推到
   現象嗎？只有「是快取問題」這種結論就追問中間的鏈。
3. **影響範圍**：除了眼前這個現象，有沒有連鎖影響（別的排程讀到舊資料、別的議題的根因
   其實是這個）？
4. **修法**：有沒有分層——立即止血／根本修／可觀測性改善？只修眼前那筆算止血還是根治？
5. **驗證方式**：別人能照跑的查證指令（SQL／API query）？能打勾的驗收條件（例如
   「冪等雙跑第二次 0 筆」）？

## 步驟 5 — 組稿，給使用者確認

**組稿完整遵守 `redmine` skill「寫入 Redmine 的基本準則」（規格
"#26311":https://redmine.nineder.com/issues/26311 ）的全部條款**，重點：

- **標題**套公式：`[系統/模組] 一句話現象 — 根因或量化影響`
- 內文依分流結果組五段結構，**填不出來的段落整段刪除，不留空模板骨架**
- 數據對帳用 Textile 表格（`|_.` 表頭）；code／log **不分行數**一律用 `<pre>` 包起來（語言
  在 Redmine 內建清單內時裡層加 `<code class="lang">`）、再用 `{{collapse(標題)...}}` 收合、
  收合外面補一句結論（舊的「超過 10 行才收合」門檻已廢除）
- **行內的 `@...@` 不能包角括號標籤**——會讓那一行之後整份文件的表格全部不解析，而且
  Redmine 不報錯；要講標籤就寫「pre 標籤」這類文字敘述（#26311 v5 第 7 條）
- 超連結（`"文字":https://...`）前後留半形空白，不緊貼中文字
- 引用其他議題寫 `{{issue(id)}}` 或 `"#id":URL`

完整貼給使用者看過一遍，明確問「這樣可以建立了嗎？」——**在使用者明確同意之前，不要呼叫
`create_issue`**。

## 步驟 6 — 建立議題

使用者確認後才呼叫 `create_issue`：`project_id`、`subject`、組好的 `description`、
`tracker_id` 用 Bug。priority 依影響建議：正式環境資料錯誤／金流／客訴級建議 High 以上，
並跟使用者確認。缺必填欄位（常見 `assigned_to_id`／`due_date`）時錯誤訊息會指出缺什麼，
跟使用者確認後補上重試。建立成功後回報議題連結。

### 步驟 6.5 — 參考議題自動建立正式關聯

訪談中提過的其他議題（「根因來自 #X」「連鎖影響到 #Y」「跟 #Z 很像」），建立成功拿到新
議題 id 後，逐一呼叫 `create_issue_relation`（`relation_type` 預設 `relates`；語意明確
指向其他類型才用 `blocks`/`duplicates` 等），讓議題頁的 Related issues 出現正式雙向關聯，
不是只有文字提及。

**不要為了表示「有關」或「後續工作」就用 `precedes`/`follows`**——那會讓 Redmine 自動重排
後續議題的 start_date/due_date（開始日推到前置議題到期日的隔天，到期日依工期往後平移），
過程沒有任何提示（實例 #26537 被改成 2026-10-01/2026-12-17）。只有真的要表達排程先後、而且
接受日期被自動計算才用；誤設後刪掉關聯不會還原日期，要用 `update_issue` 改回去。

## Status 分工

與 `redmine-feature-create` 同一套規則（規格見
"#26313":https://redmine.nineder.com/issues/26313 ）：建立時預設 New 不用問；使用者本身是
開發人員且表明立刻動工，才問「要不要直接設 In Progress？」。如果訪談發現這其實是某張
**已 Closed 議題**的延續，主動提醒二選一：同一件事的延續 → Reopen 舊議題；新範圍 →
開新單並 relation 回舊議題——不要默默把新問題塞進已結案議題。

## 最終檢驗標準

這張 Bug 單如果現在指派給一個完全沒參與過討論的工程師，或丟給另一個沒有上下文的 Claude
對話，**能不能單看內容就知道去哪裡查、怎麼重現（或怎麼驗證根因）、怎麼判斷修好了**——
如果不確定，代表訪談還沒問到位，回到步驟 3／4 繼續追問。
