# Redmine 需求撰寫（特性描述 + 驗收標準）

這份 skill 不是發明新格式——公司已經有固定的 Feature 議題範本（特性描述 + 驗收標準 +
附加資訊），且過去兩年多的 Feature 議題幾乎都是照這個格式填。這份 skill 做的事，是把「同
樣格式但寫得好 vs 寫得弱」的真實落差歸納出來，讓填的人知道每一格該填到多具體，才能讓後續
工程師少來回問、需求少反覆變動。

判斷依據來自 2024/10 ~ 2026/07 期間、實際包含這兩段內容且填寫詳細的 Feature 議題抽樣
（例如 #25940、#25430、#24218、#23199、#23078 等），對照同期填得很籠統、後續在 journal
裡反覆補問才把需求問清楚的案例（例如 #25397、#25181、#23926、#24771 等）。

**定位**：這是**被動**的撰寫規範／review 用 skill，**絕不執行任何 Redmine 寫入動作**——
需要「實際建立議題」時是另一個 skill `redmine-feature-create` 的事。本 skill 的規格單一事
實來源是 Redmine 議題 "#26312":https://redmine.nineder.com/issues/26312 （並繼承
"#26311":https://redmine.nineder.com/issues/26311 基本寫入準則的全部條款）——之後要修改本
skill 的內容，先修訂 #26312 再同步這份檔案。

## 先辨識情境：需求者提需求 vs 開發者快速 Note

同一份三段式範本要吃下兩種情境，進來先判斷是哪一種：

| 情境 | 訊號 | 產出重點 |
| --- | --- | --- |
| **需求者提出需求** | 語句指向「未來要做什麼」——想要、希望、需要新增、應該可以… | 三段式寫滿寫具體，讓工程師不追問就能開工（下面「三段式結構」全套適用） |
| **開發者快速 Note** | 語句指向「已經做了什麼」——我把、已經、改好了、跑完了、剛部署… | 骨架可精簡，但**留痕欄位必填**（見「開發者快速 Note」段） |

**辨識不出來就問一句**「這是要提出的需求，還是已經做完要留 Note？」——不要自行預設。

## 三段式結構

### [特性描述(Feature Description)] — As a / I want / so that

| 欄位 | 要填什麼 | 太弱的寫法 | 具體的寫法 |
| --- | --- | --- | --- |
| 身為 (As a) | **具體的角色或系統**，不是誰都適用的泛稱 | 「使用者」「行銷人員」「開發者」 | 「有綁定 Select99 團主身份（Reseller）的團購主以及他旗下有綁定小幫手的帳號」「組織內任何需要用多台電腦、或需要用不同 Redmine 帳號存取 Redmine 的成員」 |
| 我想要 (I want) | **具體的功能/機制**，講得出「做什麼」，不是只講方向 | 「加速建立版本的時間和簡化操作」「蒐集使用者在前端頁面的行為數據」 | 「透過一個組織層級的 `/redmine` Skill，自動偵測這台電腦是否已設定好 MCP 連線……」「於團購主專區介面內，新增一個『接案專區』，可線上知道各案件條件詳情決定是否承接……」 |
| 以至於 (so that) | **可被檢驗的效益**，講得出「怎麼知道有達到」 | 「做出更多精細的分析」「賺錢」 | 「每台電腦都能各自用正確的 Redmine 身份操作、彼此互不影響，且整個組織任何成員在任何電腦上第一次用都能自己上手」 |

**判斷方法**：把這三格連起來讀一遍，如果讀完仍然「換一批人來看，各自會做出不同的東西」，
就是太弱——通常是角色沒指名、動詞太籠統、效益沒有可驗證的終點。

### [驗收標準(Acceptance Criteria)] — Given / When / Then

| 欄位 | 要填什麼 | 太弱的寫法 | 具體的寫法 |
| --- | --- | --- | --- |
| 假定 (Given) | 情境的**起始狀態**，最好能對到實際系統狀態、欄位值、頁面路徑 | 「已模組化」（把要做的結果當成前提，等於沒講） | 「被推播者『團購主』及『小幫手』已經綁定 LINE，有 GosubarID，且 `customer_info.be_reseller` 有『團購主』`reseller_info.id`」 |
| 當 (When) | **會觸發的動作或時間點** | 「進行操作」「使用者到了某個狀態」 | 「輸入 `/redmine XX`」「對帳業務勾選後 `reseller_bill.status = pending_apply`」 |
| 然後 (Then) | **可觀察、可驗收的結果**，能對照著實際畫面/資料去打勾 | 「可以記錄下來，提供以後分析」（沒講記錄成什麼、存哪、以後怎麼用） | 「19:00 PM 產出」→ 下一列再接一組 Given/When/Then「隔天早上 9:00」/「陸續推播給『團購主』及『小幫手』」 |

**多步驟流程不要硬塞進一組 GWT**：如果需求本質是一個狀態機或多階段流程（例如審核流程、
分潤流程、開團流程），就重複填多組 當(When)/然後(Then) 列，一步一狀態往下接，最好每個狀態
都能連結到實際的畫面 bookmark 或後台篩選視圖（參考 #23199 的 8 段狀態流程寫法）。

**什麼時候可以留白**：如果附加資訊已經放了完整的畫面設計稿連結（Figma/Google
Drive/Xmind），而且特性描述本身已經把每個畫面情境講清楚，驗收標準留白是可接受的（參考
#25224）。但如果附加資訊也是空的、特性描述也籠統，留白就只是「沒想清楚」，不是「不需要」。

### [附加資訊(Additional Information)] — 技術細節與參考資料的正確位置

這段是**真正決定工程師能不能少問幾次的地方**。好的附加資訊通常包含以下任一種：

- 畫面設計稿連結（Figma / Google Drive 資料夾 / 截圖）
- 既有 API 文件、規格連結，或指出要串接的既有系統/端點
- 架構圖、side-bar 結構圖等視覺化說明
- 技術背景與已知限制（哪些做法試過不可行、為什麼）
- 相關議題連結：parent issue、拆解出的 sub-issue、之前類似需求的議題編號
- 明確的階段順序（例如「先做英文就好」「這期只做 A，B 之後再排」）

空白的附加資訊本身不是問題（單純的小功能不需要），但如果特性描述和驗收標準都偏籠統、
附加資訊又是空的，這張需求單幾乎必然會在 journal 裡靠好幾輪往返把細節問出來。

## 開發者快速 Note（做完之後回填留痕）

開發者情境求快，骨架可以精簡，但**不是可以少寫**——少的是敘事，不是事實。

### 骨架改成回顧式

| 欄位 | 開發者 Note 要填什麼 |
| --- | --- |
| 身為 (As a) | 實際執行的角色或系統（哪個服務／哪台機器／哪個 plugin） |
| 我想要 (I want) | 實際**做了什麼機制**，不是打算做什麼 |
| 以至於 (so that) | 解決掉哪個可驗證的問題 |
| 假定 (Given) | 改動前的狀態 |
| 當 (When) | 實際下的動作或指令 |
| 然後 (Then) | 改完後觀察到的結果與驗證方式 |

可以短，但**不可以只寫「已完成」**這種沒有內容的句子。

### 留痕三件事（附加資訊必填）

**1. Git commit —— 只要這次工作有 commit 就必須留連結**

來源是 <https://gitlab.nineder.com>。逐條列出，多個 commit 就多列，跨 repo 就分組：

```
Repository: nineder/claude/plugin/redmine
Branch: main
Commit: 47f2e4f — 3.1.3: redmine-bug spec v1.2
Link: https://gitlab.nineder.com/nineder/claude/plugin/redmine/-/commit/47f2e4f
```

不可只寫「已 commit」，也不可只給 hash 不給連結。

**2. GCP Machine —— 只要動到機器就必須留名稱＋連結**

「動到」包含：建立、刪除、改規格、改開機設定、改防火牆／網路、重啟。格式：

```
Machine: redmine-test-nineder-plugin
Project: nineder-admin ｜ Zone: asia-east1-b
Link: https://console.cloud.google.com/compute/instancesDetail/zones/asia-east1-b/instances/redmine-test-nineder-plugin?project=nineder-admin
```

只改機器內的軟體設定、沒動到機器本身，一樣要列出機器名稱，並註明改的是哪個服務／檔案。

**3. 重大結論／異動記錄 —— 寫在 Description 底部的固定清單**

附加資訊最後放一個表，逐條「日期 — 結論或異動 — 依據連結（commit／機器／議題）」，讓未來
review 時**單看 Description 就掌握全貌**，不必翻 journal。

判定「重大」的門檻（符合任一即是）：

- 改變架構或流程
- 改變對外行為或介面
- 推翻先前的決策
- 造成資料或環境不可逆的變更
- 影響其他人既有的作業方式

**過程細節（試了什麼、失敗原因、討論往返）仍寫 journal Note，只有結論上 Description。**
新增條目時先讀最新版 Description 再往清單追加，**不覆蓋既有條目**。

## 撰寫前自我檢查清單

1. 「身為」那格換成別的同事來看，會不會想成別的角色？如果會，要寫更具體。
2. 「我想要」那格，講的是「做什麼」還是只是「想要更好」這種方向性語句？
3. 「以至於」那格，有沒有一個可以檢驗「有沒有達到」的具體結果？
4. 「假定」那格是不是把「做完之後的結果」誤當成了前提？（常見錯誤）
5. 需求是不是本質上有多個步驟/狀態？如果是，有沒有拆成多組 When/Then？
6. 有沒有現成的畫面稿、API 文件、既有系統的欄位/端點可以直接連結到附加資訊，而不是等
   工程師自己來問？
7. 這張單子如果現在指派出去、完全沒有後續討論，工程師能不能直接開工？如果答案是不確定，
   通常代表某一段還太籠統。

開發者 Note 情境額外檢查：

8. 這次工作有 commit 嗎？有的話 repo 路徑、branch、hash、連結四項都齊了嗎？
9. 有動到 GCP 機器嗎？機器名稱、project、zone、Console 連結都齊了嗎？
10. 這次有沒有符合「重大」門檻的結論或異動？有的話進了 Description 的記錄清單了嗎？

## 給 review 別人需求單時使用

當使用者請你檢查/潤飾一份別人寫的 Feature 需求描述時，依上面的判斷方法逐格對照，具體指出
哪一格太籠統、可以怎麼改得更具體（可引用上面對照表的寫法），而不是整份重寫一遍——保留原本
的業務語意，只把模糊的角色/動詞/效益/前提換成可驗證的版本。
